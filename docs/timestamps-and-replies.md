Run `supabase/inspect_content_schema.sql` in the Supabase SQL Editor to check the
actual columns, defaults, foreign keys, policies, and timestamp triggers. If the
reply table already has `parent_reply_id`, `reply_to_user_id`, or an equivalent,
review that schema before deploying this simple mention implementation.

If both `created_at` columns already use `TIMESTAMPTZ NOT NULL DEFAULT now()`,
no migration is needed. Otherwise, run
`supabase/migrations/202610200001_content_created_at.sql` after reviewing the
inspection results. It adds missing columns and configures database defaults
without updating existing timestamps. The entire transaction rolls back if an
existing column is not timezone aware or historical records have missing dates.
Backfill missing dates from trusted historical data before retrying; do not
invent old creation times. For a nonempty table without a column, first add
`created_at TIMESTAMPTZ` without a default, populate authentic dates, then rerun.

If an existing column is `timestamp without time zone`, confirm the timezone it
historically used. Only if it was UTC, convert with:

```sql
-- Run only for the table(s) confirmed to store UTC without a timezone.
alter table public.posts alter column created_at type timestamptz
  using created_at at time zone 'UTC';
alter table public.replies alter column created_at type timestamptz
  using created_at at time zone 'UTC';
```

Do not run those conversions on columns that are already `timestamptz`.

## RLS and credentials

No policy change is required by these features: they use the existing reads,
reply INSERT, post foreign key, and profile joins. Keep RLS enabled. The Android
client still uses only `SUPABASE_PUBLISHABLE_KEY`. Gradle no longer reads or
generates a `SUPABASE_SECRET_KEY` BuildConfig field. `.env` is not packaged or
loaded by the app.

The current publishable credential needs verification in Supabase Project
Settings / API Keys, since the schema request was unauthorized. A 401 does not
establish an RLS policy problem. Never substitute the secret key to fix it.

If authenticated inserts or refetches fail after the credential is corrected,
inspect the SQL policy output. Required permissions are INSERT on `replies`,
SELECT on the visible reply/post, and SELECT on the permitted author profiles.
An INSERT policy must enforce `auth.uid() = user_id`; SELECT policies must match
the project's intended post visibility. If these policies are missing, the
following are conditional templates, not automatically applied migrations:

```sql
-- Review existing policies first; permissive policies combine with OR.
create policy "Users insert replies on visible posts" on public.replies
for insert to authenticated
with check (
  (select auth.uid()) = user_id
  and exists (select 1 from public.posts p where p.id = replies.post_id)
);

create policy "Users read replies on visible posts" on public.replies
for select to authenticated
using (exists (select 1 from public.posts p where p.id = replies.post_id));
```

These depend on existing `posts` SELECT RLS to define visibility. If reading
profiles is restricted, review the existing profile SELECT policy rather than
granting access to every profile. Do not disable RLS or broaden visibility to
make a join work. A missing username leaves the Reply action disabled, rather
than generating a mention from a display name or a placeholder.

## App behavior

Creation times are generated by Postgres, never supplied in post/reply insert
DTOs. Existing refetches load the real database time after creation. The shared
formatter parses UTC/offset timestamps (including fractional seconds), compares
instants for minute/hour ages, and uses the device timezone for calendar days and
years. It displays hours for content less than 24 hours old, Yesterday for the
previous calendar day thereafter, days through six days, then a date (including
the year when different). Labels refresh every 30 seconds while composed.
Missing or malformed times are omitted, never replaced with the device time.

Each Reply action prepends `@profiles.username `, preserves the existing draft,
places the cursor after the mention, focuses the field, and opens the keyboard.
The same leading username is not duplicated (case insensitive, whole handle).
Submitting persists the full text, including mentions, in `replies.content`
with the existing `post_id` and authenticated `user_id`. Outer whitespace is
trimmed as before. Reads preserve the text and highlight handles. There are no
new reply columns, nested threads, notification behavior, or navigation changes.
